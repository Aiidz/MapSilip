# Staff access SQL review candidates

The approved authorization and RLS-probe SQL batches were applied to the MapSilip project through Supabase MCP and are recorded as remote migrations `20261025081017 staff_authorization` and `20261025081034 staff_security_probes`. Exact copies are tracked locally under `supabase/migrations/`. The Storage probe remains unapplied. The local Supabase CLI and application executor credential are not configured. Preserve the permanent project: do not reset, drop, truncate, or clean up these objects.

The applied `staff-authorization.sql` defines private staff authority, session admissions tied to Supabase Auth session IDs and current account revisions, and a caller-only snapshot RPC. RLS is enabled on private tables with no client table grants/policies. New accounts default to requiring password change. Every authority-row update advances the revision; status/role changes restore the restriction. Reissue must advance authority before credentials are changed or delivered. Re-activation/recovery flows are not implemented. Mutation commands lock the account and attempt rows in account-then-attempt order. `can_read` and the snapshot are non-locking `STABLE` functions so they can run in RLS and read-only GET/HEAD transactions; they cannot serialize an in-flight read against a concurrent deactivation. Subsequent statements observe the committed revision/status change, but the exact in-flight race behavior requires hosted runtime tests. No custom Auth/session tokens are proposed.

The lookup's narrow SECURITY DEFINER function is intentional: it must read otherwise inaccessible authority/Auth data without recursive RLS. Review its trusted owner, empty search path, qualified objects and restricted EXECUTE grants. Private schema usage grants no table access. No user/session selector is accepted. Membership checks row existence for revoked sessions; it does not independently implement Supabase's timebox/inactivity expiry settings.

The applied SQL includes a `complete_first_login` command, and the local backend has a server-only executor path for it. That command trusts its caller's confirmation booleans; only the trusted server may call it after Supabase Auth confirms a password update and global sign-out, then a fresh sign-in. SQL alone does not prove the Auth mutation happened. The SQL is installed, but no Auth users or executor credential exist yet, so there is no tested unlock path. Multiple admissions are representable, but completion requires exactly one live session and only admits that fresh session. No custom Auth/session token is used.

`staff-probes.sql` is now applied as an RLS fixture. It creates two public marker tables with one fixed synthetic marker row each and policies for general staff-read and owner-only finance-read checks. An anonymous direct GET, HEAD, and snapshot RPC each returned HTTP 401. No authenticated positive controls have run because the two synthetic staff identities and executor credential are not yet provisioned. `staff-storage-probes.sql` remains an independent optional Storage fixture and has not been applied. Existing permissive Storage policies could bypass new policies, so inspect the full policy set before any later Storage fixture approval. Previously issued signed URLs need separate tests; they do not automatically become revoked merely because a user is deactivated.
