# Backend foundation boundaries

The login and mandatory first-login password replacement forms call the server-side Auth endpoints. The profile menu exposes sign-out only when staff Auth is enabled. Management and Caretaker layouts verify the current server-owned account/session snapshot and enforce the matching role when enabled; with the gate off, the existing credential-free UI preview remains available. Keep `MAPSILIP_STAFF_AUTH_ENABLED=false` until the hosted migration and Auth/session/RLS/Storage security gates pass. No operational records API is implemented.

- `server.ts` is the request-scoped server entry point; its dependency on `next/headers` keeps it out of Client Components. `getVerifiedIdentity()` uses Auth's `getUser()` and returns only a user ID. `executeStaffOperation()` additionally reads the current server-owned access snapshot through `mapsilip_staff_access_snapshot` before invoking a server-defined action. `requireStaffAccess()` is used by the diagnostic probe. Neither a verified identity nor this application-layer preflight replaces RLS or transaction-level authorization.
- `staff-access.ts` validates trusted access snapshots and denies missing, malformed, deactivated, first-login-restricted, stale-session, unknown-role and unapproved-action cases. Caretakers have no operational actions approved in this scaffold; confirmed owner actions are explicit. The application preflight does not replace authorization in RLS or transactional commands.
- `auth/service.ts` implements server-side sign-in, mandatory password-change and sign-out orchestration. `POST /api/auth/signin`, `/api/auth/first-login` and `/api/auth/signout` validate origin as applicable, use the narrow executor and verified Auth sessions, buffer cookies until database confirmation (or database grant revocation for sign-out), and return sanitized `private, no-store` responses. The exact feature flag keeps these routes unavailable by default. The first-login page is presentation only; its POST endpoint verifies the restricted session and one-time server attempt. No tenant self-registration or operational data endpoint is implemented.
- `executor.ts` uses a narrowly named PostgreSQL executor role and fixed parameterized function calls; it rejects role privilege or membership mismatches. The configured executor URL and HMAC secret are server-only. This adapter has not been tested against a hosted database.
- `supabase/review/staff-authorization.sql` now includes the proposed account/session/attempt tables, triggers, read-compatible STABLE checks, mutation commands including first-login completion, and explicit grants. `staff-probes.sql` proposes synthetic RLS and private Storage probes. These are review candidates, not registered or applied migrations. They have not been parsed or executed by PostgreSQL; hosted Auth, RLS, Storage and concurrency behavior remain unverified.
- `identity.ts` has no role mapping and never authorizes from editable metadata or a stored session snapshot. Provider/network errors deny identity verification. Offline tests use a provider-boundary stub; they do not demonstrate Supabase behavior.
- `security.ts` provides sanitized public errors, an exact trusted-origin mutation check and exact allowlisted return paths. The trusted origin and allowed destinations must come from server configuration/current permission checks. They must never come from submitted fields or Host/forwarded headers. The origin helper permits HTTP loopback only outside production; hosted origins require HTTPS. Origin validation supplements Next.js protections, authentication and rate limiting.
- `../supabase/` owns environment validation and browser/server transport. No administrative client exists. Server cookies are read-only by default; writable adapters preserve all chunks/options/deletions and surface persistence failures. A partial write must abort the future operation/response; it is not transactional or confirmed session refresh.

For future handlers: validate method/origin, parse input as unknown, validate an explicit field allowlist and bounded lengths/types, verify identity, check authoritative current access/session/permission, then call an approved transactional domain operation. Return only sanitized errors and intentional response fields. Use `Cache-Control: private, no-store` on personalized responses; do not cache identity/access checks across requests. No generic CRUD or client-selected role/user ID should bypass these steps. Use the installed SDK error types/codes to classify failures and approved rate limiting before exposing endpoints.

`npm test` compiles the small pure TypeScript modules into an automatically removed temporary directory with the installed TypeScript compiler, then uses Node's test runner. This works without Node's experimental TypeScript stripping, credentials, network access or Docker. Full application typechecking remains `npm run typecheck`. Unit tests cover configuration, cookie persistence, identity-boundary failures, origin attacks, redirects, error sanitization and staff-guard decisions using trusted-provider fixtures. These fixtures do not prove Supabase Auth session provenance, SQL correctness, RLS, Storage, revocation, or concurrency behavior. Runtime Auth/RLS/Storage tests are a separate release gate; mocks cannot close it.

No operational migrations or business-data APIs exist. The preflight script is read-only and requires an explicit opt-in plus a locally approved hash manifest; it does not apply SQL or create fixtures. The test suite uses offline/provider-boundary fixtures and is not evidence of hosted Auth, database, RLS, Storage or race behavior. Do not connect the login UI or enable staff access until the hosted acceptance tests pass and activation is separately approved.
